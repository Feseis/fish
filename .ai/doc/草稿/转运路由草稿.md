# 转运路由草稿

状态：草稿（不长期维护）
用途：运输线路、路由规则、车辆与交接单的结构讨论稿；定稿后分流至决策日志与待办。
更新时间：2026-11-09

## 已裁决口径

### 路由模型

- **静态分级路由，不实时计算**。线路与规则预先配置，运行时只做查询。
- 线路两端必须是网点（`logistics_site`），不能指向自由地址。
- 运输时**逐跳查询**，不在运单上预存完整路径。
- 可达性不是「目的地有没有网点」，而是「收件区县是否被营业网点覆盖」：下单时用 `receiver_adcode` 查 `logistics_site_area`，查不到即超区，拒绝下单。
- 支线与默认路由规则由系统按网点层级生成；干线、例外规则、区县覆盖由管理员配置。
- 线路与规则均不物理删除，停用置 `enabled=0`；历史交接单存网点与车牌快照，不受改线影响。

### 线路约束

- `1支线`：一端是营业网点（`site_type=1`），另一端是转运中心（`site_type=2`），方向不限。
- `2干线`：两端都是转运中心。
- 驿站（`site_type=3`）不参与路由，只作为末端派送方式。
- 同一起终点同一类型只允许一条线路，不拆班次；发车时间记在交接单上。

### 车辆

- 公司车辆单独建表，交接单引用 `vehicle_id` + 车牌快照。
- 支线车归营业网点，干线车归转运中心，由应用层校验。
- 派车时校验 `vehicle.status=1`，维修或停用的车不能建交接单。
- 不做年检、保险、保养、GPS、油耗、装载率统计。

### 交接

- 一张交接单对应一趟车（一车多票），运单明细在 `handover_item`。
- 交接单记录交出/接收网点快照、车牌快照、交接人姓名快照、司机姓名快照。
- 到达时更新 `arrived_at` 与 `status=2`。
- 司机字段先留，司机申请渠道尚未开放（`logistics_staff.staff_role=3` 有码值，无入口）。

### 退回路由

- **原路返回为主**：按正向已完成的 `handover` 段倒序逐段逆向，不重新规划路径。
- 每段交换起点终点，`direction=2`；同一条 `transport_line` 双向使用，逆序时起终点与线路定义相反是合法的。
- 正向已停用的线路，退回仍可使用；正向建单仍要求线路 `enabled=1`。
- 网点停用后查 `logistics_site_merge` 解引用，把起终点替换为最终网点；撤并链最多 5 层。
- 只有「撤并替换后线路不存在」时才用 `route_rule` 兜底，按寄件 adcode 查下一跳；仍查不到则转人工。
- 退回终点是原揽收网点（经撤并解引用后的网点），不按 adcode 重新选择。
- 在途退回（`3运输中` 发起）不中断当前段：正向 `status=1` 的在途段不参与逆向，等它到达后再从该段终点开始退回。
- 退回运费由寄出者二次支付，**不阻塞退回运输**；欠费只标记，支付细节见 `支付表草稿.md`。

## transport_line

```sql
CREATE TABLE transport_line (
  transport_line_id CHAR(36)         NOT NULL COMMENT '线路主键 UUID',
  line_code         VARCHAR(24)      NOT NULL COMMENT '线路编码，如 ZX-HZ-SH-01；唯一且不回收',
  origin_site_id    CHAR(36)         NOT NULL COMMENT '起点网点 → logistics_site.logistics_site_id',
  dest_site_id      CHAR(36)         NOT NULL COMMENT '终点网点 → logistics_site.logistics_site_id',
  line_type         TINYINT UNSIGNED NOT NULL COMMENT '1支线(营业网点↔转运中心) 2干线(转运中心↔转运中心)',
  transit_hours     SMALLINT UNSIGNED NOT NULL COMMENT '标准时效，小时',
  enabled           TINYINT          NOT NULL DEFAULT 1 COMMENT '1启用 0停用；不删行，历史交接单仍需渲染',
  created_at        DATETIME         NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at        DATETIME         NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (transport_line_id),
  UNIQUE KEY uk_line_code (line_code),
  UNIQUE KEY uk_origin_dest (origin_site_id, dest_site_id, line_type),
  KEY idx_origin (origin_site_id, enabled),
  KEY idx_dest (dest_site_id, enabled)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_general_ci
  ROW_FORMAT=DYNAMIC COMMENT='运输线路表';
```

## route_rule

```sql
CREATE TABLE route_rule (
  route_rule_id      CHAR(36)     NOT NULL COMMENT '规则主键 UUID',
  current_site_id    CHAR(36)     NOT NULL COMMENT '当前网点 → logistics_site.logistics_site_id；只允许 site_type=1/2',
  dest_adcode_prefix VARCHAR(6)   NOT NULL COMMENT '目的地区划前缀，如 33（省）、3301（市）、330106（区县）',
  transport_line_id  CHAR(36)     NOT NULL COMMENT '下一跳线路 → transport_line.transport_line_id',
  enabled            TINYINT      NOT NULL DEFAULT 1 COMMENT '1启用 0停用',
  created_at         DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at         DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (route_rule_id),
  UNIQUE KEY uk_site_prefix (current_site_id, dest_adcode_prefix),
  KEY idx_line (transport_line_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_general_ci
  ROW_FORMAT=DYNAMIC COMMENT='路由规则表';
```

匹配方式：`收件 adcode LIKE CONCAT(dest_adcode_prefix, '%')`，按 `CHAR_LENGTH(dest_adcode_prefix)` 倒序取第一条。`dest_adcode_prefix` 只允许 2、4、6 位，分别对应省、市、区县；最长前缀优先。数据量小，全表扫描可接受，不为前缀匹配单独建索引。

## logistics_site_merge

```sql
CREATE TABLE logistics_site_merge (
  logistics_site_merge_id CHAR(36)     NOT NULL COMMENT '撤并记录主键 UUID',
  from_site_id            CHAR(36)     NOT NULL COMMENT '被撤并网点 → logistics_site.logistics_site_id',
  to_site_id              CHAR(36)     NOT NULL COMMENT '并入网点 → logistics_site.logistics_site_id',
  merged_at               DATETIME     NOT NULL COMMENT '撤并生效时间',
  operator_name           VARCHAR(64)  NULL     COMMENT '操作人姓名快照',
  created_at              DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (logistics_site_merge_id),
  KEY idx_from_time (from_site_id, merged_at),
  KEY idx_to (to_site_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_general_ci
  ROW_FORMAT=DYNAMIC COMMENT='网点撤并记录表';
```

网点表不加字段，撤并历史全部留在本表。查询最新去向：

```sql
SELECT to_site_id
FROM logistics_site_merge
WHERE from_site_id = ?
ORDER BY merged_at DESC
LIMIT 1
```

解引用算法：

```
site = 原网点
depth = 0
while site.enabled = 0 and depth < 5:
    merge = 查 from_site_id = site 的最新记录
    if merge is null: 纯停用，转人工
    site = merge.to_site_id
    depth++
if depth >= 5: 撤并链异常，转人工
return site
```

三种情况分开：

| `enabled` | 撤并记录 | 处理 |
| --- | --- | --- |
| 1 | — | 直接使用 |
| 0 | 有 | 跳到新网点，继续解引用 |
| 0 | 无 | 纯停用，无人接收，转人工 |

撤并只允许同 `site_type` 之间进行。一个事务内做五件事：

1. 旧网点置 `enabled=0`；
2. 写一条 `logistics_site_merge`；
3. 若两者都是 `site_type=1`，把 `logistics_site_area` 中旧网点负责的区县改到新网点；
4. 把下级网点的 `parent_logistics_site_id` 从旧网点改到新网点；
5. 把 `logistics_staff.logistics_site_id`、`vehicle.logistics_site_id` 从旧网点改到新网点。

正向下单反查因此永远命中可用网点，退回原路则靠历史表解引用。

## handover

```sql
CREATE TABLE handover (
  handover_id       CHAR(36)     NOT NULL COMMENT '交接单主键 UUID',

  transport_line_id CHAR(36)     NOT NULL COMMENT '→ transport_line.transport_line_id',
  direction         TINYINT UNSIGNED NOT NULL DEFAULT 1 COMMENT '运输方向：1正向 2退回',
  from_site_id      CHAR(36)     NOT NULL COMMENT '交出网点快照 → logistics_site.logistics_site_id',
  to_site_id        CHAR(36)     NOT NULL COMMENT '接收网点快照 → logistics_site.logistics_site_id',
  vehicle_id        CHAR(36)     NULL     COMMENT '→ vehicle.vehicle_id；无车运输为空',
  vehicle_plate     VARCHAR(16)  NULL     COMMENT '车牌快照，发车时写入，之后不随车辆换牌更新',

  operator_name     VARCHAR(64)  NULL     COMMENT '交接人姓名快照；与司机可能不是同一人',
  departed_at       DATETIME     NOT NULL COMMENT '发车时间',
  arrived_at        DATETIME     NULL     COMMENT '到达时间；在途为 NULL',
  status            TINYINT      NOT NULL DEFAULT 1 COMMENT '1在途 2已到达',
```

## 转运流程

```
揽收网点装车
  → 查 route_rule：current_site_id=揽收网点，收件 adcode 最长前缀匹配
  → 命中 transport_line
  → 校验 vehicle.status=1
  → 建 handover（status=1）+ handover_item
  → 写轨迹「离开」，operator_type=3、operator_id=交出网点

到达下一站
  → handover.arrived_at=now()、status=2
  → 写轨迹「到达」，operator_type=3、operator_id=接收网点
  → 若接收网点就是派送网点，运单仍是 3运输中

快递员开始派送
  → 写轨迹「派送中」（动作码 4），运单置 4派送中
```

到达派送网点不等于开始派送：两者之间可能隔夜或排队，轨迹分开写，`status_after` 分别是 3 和 4。

查「这票货现在在哪」：按 `waybill_id` 取最新 `handover_item`，再取对应 `handover.status=1` 的记录；没有在途交接单说明货停在某个网点。

轨迹与交接单不互相存外键：轨迹只记「到达/离开」，交接单只记批次与明细，需要关联时按 `waybill_id + 时间` 对齐。

## 退回流程

```
① 发起退回（4派送中拒收 / 7异常决定退回 / 3运输中取消联动）
   写 waybill_return，运单置 8退回中，写动作码 9 轨迹

② 取正向已完成的路径
   SELECT h.transport_line_id, h.from_site_id, h.to_site_id
   FROM handover_item hi
   JOIN handover h ON hi.handover_id = h.handover_id
   WHERE hi.waybill_id = ? AND h.direction = 1 AND h.status = 2
   ORDER BY h.departed_at DESC
   当前网点 = 最后一段的 to_site_id；没有正向段则为揽收网点

③ 判断是否存在正向在途段（direction=1 AND status=1）
   有：本次只写 waybill_return、运单置 8、写动作码 9 轨迹，暂不建退回交接单；
       等该段到达并置 status=2 后，由到达事件重新执行 ②③ 并创建第一张退回交接单
   无：立即从当前网点逐段逆向，每段交换起终点：from' = 原 to，to' = 原 from

④ 两端解引用撤并
   from' = 解引用(from')
   to'   = 解引用(to')
   若 from' = to'：跳过该段
   若替换后线路不存在：查 route_rule 兜底

⑤ 建退回交接单
   handover(direction=2, status=1) + handover_item
   写轨迹「离开」，status_after=8

⑥ 到达最终网点
   handover.arrived_at、status=2
   写轨迹「到达」，status_after=8
   联系寄件人签收，写动作码 10「退回签收」
   waybill_return.completed_at=now()，运单置 9已退回
```

在途退回：正向 `status=1` 的在途段不参与逆向，等它到达并置 `status=2` 后，再从该段终点开始退回。当前这一段不中断，避免车辆中途掉头。

退回终点不是按 adcode 重新选的，而是原揽收网点经撤并解引用后的网点。只有替换后线路不存在时，才用 `route_rule` 按寄件 adcode 兜底；仍查不到则货物停在当前网点，写异常转人工。

## 路由规划与校验

取下一跳固定按两级顺序：

1. **先查规则**：按 `current_site_id = 当前网点` 且 `dest_adcode_prefix` 是目的 adcode 的最长前缀取 `route_rule`，命中即用该规则指定的线路。规则只用于干线与例外，营业网点通常不配。
2. **再走层级默认**：未命中且当前是营业网点时，固定走「到 `parent_logistics_site_id`（转运中心）」的支线；当前是转运中心时视为断链。

营业网点不配规则，是因为层级已经由 `parent_logistics_site_id` 唯一确定；若给每个网点按 34 个省级前缀各配一条，网点数乘 34，改层级还要整体重配。

系统负责三件事：

1. **生成默认支线**：每个营业网点 → 其 `parent_logistics_site_id`，以及反向支线。
2. **生成默认规则**：只给转运中心配。干线按目的地省/市指向对端转运中心；本市区县按 6 位前缀指向归属营业网点。
3. **连通性校验**：对「每个营业网点 → 每个已覆盖区县的归属网点」做可达性矩阵，同时检测路由环（A→B→A）和断链（节点无后续规则）。线路双向各配一条，该矩阵同时覆盖正向揽收与反向派送两种口径。
4. **撤并链校验**：每条 `logistics_site_merge` 链必须能在 5 层内解引用到 `enabled=1` 的网点，且不形成环（A→B→A）。
5. **规则与线路对齐校验**：每条 `route_rule` 的 `current_site_id` 必须等于对应 `transport_line.origin_site_id`，避免下一跳不从当前网点出发。

管理员负责：区县覆盖、干线、例外规则、网点撤并登记。

建交接单时按方向做一致性校验：

| `direction` | `from_site_id` | `to_site_id` | 线路 `enabled` |
| --- | --- | --- | --- |
| 1 正向 | 等于 `origin_site_id` | 等于 `dest_site_id` | 必须 1 |
| 2 退回 | 未撤并时等于 `dest_site_id`；撤并解引用后允许为新网点 | 未撤并时等于 `origin_site_id`；撤并解引用后允许为新网点 | 不校验，允许停用 |

`direction=2` 只强制 `transport_line_id` 存在；起终点因撤并解引用偏离线路端点时，按「同一条线路反向使用」处理。

另外两条与方向无关：

- 支线的一端必须是营业网点、另一端是转运中心；干线两端都是转运中心。
- 车辆归属网点必须是线路两端之一，且 `vehicle.status=1`。

**运行时防环**：即使配置期校验通过，也可能有人手工改规则制造环。建交接单前检查该运单是否已经走过同一个 `transport_line_id`，走过则拒绝装车并标异常，避免包裹在两站之间来回运。

## 与现有表的关系

- `logistics_site`：提供线路端点与网点类型。
- `logistics_site_area`：提供「区县 → 营业网点」，决定可达性与派送网点。
- `waybill_trace`：装车写「离开」（动作码 3），到达写「到达」（动作码 2）。
- 运单状态 `3运输中` 由这些轨迹推进，不新增状态。
