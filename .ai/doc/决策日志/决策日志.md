# 决策日志

状态：有效（产出物，只追加不回改）
用途：记录定型决策与踩坑，按 `D-xxx` 检索，不按时间顺序通读。
更新时间：2026-11-12

每条只写三要素：问题 / 决定 / 原因。

## D-001 失败响应使用 ProblemDetail，不引入 Result 壳

问题：接口失败时返回什么结构。
决定：成功返回裸 DTO；失败返回 RFC 9457 `ProblemDetail`，HTTP 状态由 `ErrorCode` 决定，自定义属性挂 `code`、`timestamp`。
原因：避免 HTTP 状态与 body 业务码重复表达；网关、日志、前端都能按标准结构直接识别。

## D-002 密码使用 BCrypt 哈希

问题：密码如何存储。
决定：`auth_password.password_hash` 存 BCrypt 哈希，`hash_algo` 记录算法。
原因：不可逆、自带盐，库泄露后无法还原明文。

## D-003 手机号作为唯一登录标识

问题：用账号名还是手机号登录。
决定：`auth_account.phone` 唯一，登录只接受手机号。
原因：减少一套账号命名规则，注册即验证手机号归属。

## D-004 角色拆成关联表，永久授予

问题：一个账号可以有多个角色，且后续可能扩展。
决定：`auth_role` 字典 + `auth_account_role` 多对多，无有效期字段。
原因：单列无法表达多角色；永久授予避免引入授权时效逻辑。

## D-005 一次登录一行会话

问题：会话如何建模。
决定：`auth_session` 每次登录插入一行，`session_id` 为服务端会话标识，记录 `pwd_version` 快照与过期时间。
原因：多设备天然分离，可按会话单独失效，不必按账号整体踢下线。

## D-006 refresh token 只存哈希

问题：长期令牌在库中怎么存。
决定：只存 `SHA-256(refresh_token)`，原值仅发给客户端。
原因：库泄露时无法直接冒用长期令牌；哈希不可逆且比 BCrypt 快，适合高频校验。

## D-007 短期令牌放 Redis

问题：短期令牌校验如何做到低延迟。
决定：短期令牌存 Redis 并设 TTL，到期后用 refresh 换新。
原因：避免每次请求查库；TTL 天然实现无感续签。

## D-008 环境变量由 spring.config.import 加载

问题：`a_run_env/auth.env` 怎么进入 Spring 环境。
决定：`spring.config.import: optional:file:../a_run_env/auth.env[.properties]`，用扩展名提示按 properties 解析。
原因：Boot 不原生读取 `.env`；`KEY=VALUE` 语法与 properties 兼容，无需重命名或依赖 IDE 插件。

## D-009 异常包命名为 exp

问题：`@RestControllerAdvice` 与业务异常放哪个包。
决定：`me.feseis.fish.auth.exp`。
原因：项目所有者指定；功能上等价于 exception，不额外抽象。

## D-010 会话设备信息暂不做

问题：是否需要区分登录设备。
决定：当前 `auth_session` 不存 `client_type`、`device_id`、`device_name`。
原因：先收敛认证主链路；后续需要「在线设备列表」「按设备踢下线」时再补，见待办 `F-01`。

## D-011 文档按职能分层

问题：项目文档如何组织才能控制上下文用量。
决定：`规范/`、`决策日志/`、`待办/`、`搁置/`、`接口契约/`、`操作手册/`、`草稿/`、`建库/` 分层；每份文件头部标注状态、用途、更新时间；AGENTS.md 只放文档地图。
原因：一个文件只回答一个问题，AI 按需加载；单点事实避免同一结论散落多处。

## D-012 仓库忽略策略：env 不入库，.idea 共享

问题：首次推送 GitHub 前，哪些本地文件应排除、哪些应保留。
决定：`a_run_env/*.env` 忽略，只提交模板 `a_run_env_example/auth.env`；`.idea/` 不全量忽略，`runConfigurations/`、`gradle.xml`、`vcs.xml` 等团队配置入库，本机文件由 `.idea/.gitignore` 排除；安卓构建产物由 `app/.gitignore` 的 `/build` 兜底，另补 `app/.cxx/`、`app/release/`。
原因：env 含数据库密码，推送后需轮换，提前拦住成本最低；`.idea` 共享配置体积小、能让成员开箱即用，而 `workspace.xml` 之类天然易冲突。

## D-013 环境文件统一按仓库根解析

问题：`spring.config.import: optional:file:../a_run_env/auth.env[.properties]` 在 IDE 直接运行时找不到文件，`optional:` 静默跳过，启动报 `AUTH_DB_URL` 占位符未解析（`Driver com.mysql.cj.jdbc.Driver claims to not accept jdbcUrl, ${AUTH_DB_URL}`）。
决定：以仓库根为唯一约定 cwd。`application.yml` 改为 `optional:file:./a_run_env/auth.env[.properties]`；`auth-server8081/build.gradle.kts` 的 `bootRun` 固定 `workingDir = rootProject.projectDir`；IDE 运行配置 Working directory 设为 `$PROJECT_DIR$`。
原因：`file:` 相对路径按进程 cwd 解析，原写法只在本机 cwd 恰为模块目录时成立；统一到仓库根后 Gradle 与 IDE 两种启动方式行为一致。曾被放弃的方案：保留 `../` 并要求 cwd 为模块目录（IDE 默认值不可控），以及写成绝对路径（不可移植）。

## D-014 安卓登录页首版为纯前端占位

问题：登录接口未实现时，安卓端登录页如何落地。
决定：启动页 `MainActivity` 仅保留空白背景与一个「去登录」按钮，显式跳转 `LoginActivity`；登录页用 `MaterialButtonToggleGroup` 提供密码/验证码两种模式，只做本地校验并 Toast 提示，不发起网络请求。
原因：`/auth/login` 仍规划中，先固定页面结构与入口；后续把本地校验替换为真实请求即可，不返工页面。

## D-015 登录响应统一，短信错误码沿用库表词表

问题：密码登录与验证码登录是否各自定义响应体、短信失败如何编码。
决定：两种登录共用 `LoginResponse`，`bean/dto/login` 只保留 `LoginOnPasswordRequest`、`LoginOnPhoneOnlyRequest`、`LoginResponse` 三个文件；新增错误码 `SMS_WRONG`、`SMS_EXPIRED`；发送验证码时未注册手机号复用 `NO_ACCOUNT`，不自动建号，由前端引导注册。
原因：响应字段完全一致，双份 DTO 只会带来维护分叉；两个短信错误码与 `auth_login_log.fail_reason` 既有注释词表一致，无需迁移脚本；不自动建号避免未完成注册流程就产生脏账号。

## D-016 App 图标直接使用 fish-logo 原图

问题：`fish-logo.png`（1254×1254、RGB 无 alpha、白底）如何做成启动器图标，是否裁掉白边、是否按图形本体对齐。
决定：不裁图，整张原图保留白边；自适应图标前景按 108dp 画布的 70%（75.6dp）居中贴入，白底与图标背景同色（`#FFFFFF`），按 mdpi~xxxhdpi 预烘焙 108/162/216/324/432 px 位图；不做非白像素外接框对齐，直接用整图几何中心。旧版图标（API < 26）覆盖原 webp：方形铺满、圆形按整图加圆形蒙版。移除 `<monochrome>` 层。
原因：原图图形本体实测只占高度 62.7%（宽 95.6%），按 70% 画布后本体约 47.4dp×72.3dp，符合安全区高度要求；`<monochrome>` 需要单色 alpha 蒙版，白底位图会渲染成实心方块，去掉后 Android 13 主题图标回退为原彩色图标。

## D-017 认证页采用浅色渐变 + 白色卡片，主题固定 Light

问题：登录页视觉单薄、缺少注册入口，且 DayNight 主题在深色模式下会让白卡片上的输入框文字不可读。
决定：登录/注册/首页统一为 `bg_auth_background` 渐变（`fish_bg_top`→`fish_bg_bottom`）+ 圆角 24dp 白色 `MaterialCardView`；新增 `RegisterActivity`（手机号、验证码、密码、确认密码，注册成功自动登录跳首页）；`Base.Theme.Fish` 在 `values/` 与 `values-night/` 都改为 `Theme.Material3.Light.NoActionBar`；文案颜色改用显式色值 `fish_text_primary` / `fish_text_secondary`。
原因：页面主色为浅色品牌底，只有固定 Light 才能保证输入框与文字对比度；注册与登录共用同一视觉骨架，减少后续维护分歧。

## D-018 认证服务地址运行时可配，无默认值

问题：开发调试阶段后端跑在局域网另一台机器上，写死 `BuildConfig` 基址每次换网络都要重新编译。
决定：地址存 `SharedPreferences`（`fish_prefs` / `auth_base_url`），**不设默认值**，必须由用户在首页「连接局域网」手动填写；`HttpAuthApi` 每次请求实时读取，保存即生效；首页调试面板只在 `BuildConfig.DEBUG` 显示。网络层不引第三方库，用 `HttpURLConnection` + `org.json`，refresh 令牌交给 `CookieManager`。
原因：地址未配置时统一返回 `ENDPOINT_MISSING`，避免误连到旧地址；不新增 OkHttp 依赖，减少构建期下载与离线风险。

## D-019 待办按模块拆分，`待办.md` 只做索引

问题：认证服务与客户端的未完成事项混在一个文件里，检索和收尾容易漏项。
决定：`.ai/doc/待办/` 下按模块拆为 `auth-server待办.md`、`app待办.md`，`待办.md` 只保留索引；编号体系 `S-/F-/E-/L-` 全局连续、不按文件重置。
原因：按模块读待办可减少上下文；索引层保证「唯一待办入口」不变，仍符合文档地图约定。

## D-020 安卓 release 签名自建证书，密码不入库

问题：release 包如何签名，高德所需的两个 SHA1 从哪来。
决定：仓库根生成 `keystore/fish-release.jks`（PKCS12、RSA 2048、alias `fish`、有效期 10000 天）；密码写 `key.properties`，`.gitignore` 排除 `keystore/` 与 `key.properties`；`app/build.gradle.kts` 配置阶段读取并挂到 `release`，文件缺失时回退 debug 签名。
原因：release 不能沿用公开密码的 debug 证书；私钥与密码分离且都不入库，避免泄露；条件挂载保证没有密钥的机器仍能构建。

## D-021 寄收点按三层存储，坐标统一 GCJ-02，文本地址为权威

问题：寄件表单的寄出点与送达点如何落库，一个「地址」由哪些维度描述。
决定：
- 一个地址拆三层：语义层 `province`/`city`/`district`/`detail_addr`/联系人电话；几何层 `lng`/`lat`；实体层 `adcode`/`poi_id`/`poi_name`。
- 坐标系全程统一高德 GCJ-02，不混入 WGS-84 或 BD-09，字段注释显式标注坐标系；高德 `location` 语义为「经度,纬度」，经度在前。
- 坐标拆 `lng`/`lat` 两列存 `DECIMAL(10,6)`，不用 `FLOAT`/`DOUBLE`、不用拼接字符串、不用 MySQL `POINT`/`GEOMETRY`。
- 权威顺序：`detail_addr` 为 `NOT NULL`，是唯一可送达依据；`lng`/`lat` 业务上允许为空，只用于打点、算距离与网点分区。
- 冲突以用户最终确认为准：地图拖拽后的坐标覆盖 POI 自带坐标；手输详细地址优先于 POI 标准地址。
- 运单内联 `sender_*`/`receiver_*` 快照，不存 `address_id` 外键；用户地址簿另设 `user_address` 供表单选择。
- 服务端提交时用坐标反查 `adcode` 与前端传值比对，不一致以反查结果覆盖并回写省市区文本。

原因：快递员实际按「小区 + 楼栋 + 门牌 + 电话」送达，文本地址才是最可靠的送达依据，坐标只能辅助；POI 提供稳定地点身份，可防手误与坐标漂移；运单是历史凭证，用户改地址簿或高德 POI 变更都不得改写已下单地址；跨坐标系混存会造成几百米级偏移；`POINT`/`GEOMETRY` 在 `SRID 4326` 下语义为 WGS-84，与 GCJ-02 概念冲突且需额外 TypeHandler。

## D-022 地址拆「地理缓存 + 用户地址簿」两张表，`poi_id` 作缓存键

问题：寄出点与送达点如何落库；同一栋楼不同门牌会产生大量重复行；重复解析地址会反复消耗高德 Web 服务配额。

决定：

- 一个地址拆三层：行政区（`province`/`city`/`district`/`adcode`）、锚点（`poi_id`/`poi_name`）、门牌（`detail_addr`）。
- 录入链路固定为「定位反查省市区 → 选附近 POI → 填门牌」，**POI 必选**，因此坐标必然存在；不存在「纯文本地理编码」录入路径。
- 拆两张表：`geo_address` 全局共享地理缓存；`user_address` 用户地址簿。
- 缓存键 `poi_id`，`NOT NULL` 且唯一；命中即不再调用高德。命中判定不需要联网，这是缓存能被复用的前提。
- `detail_addr` 属用户语义，只存 `user_address`；同一 POI 下不同楼层/门牌只多一行用户条目，不污染缓存。
- 主键命名规则：主键 = 表名 + `_id`，跨表引用用全名。即 `geo_address_id`、`user_address_id`；弃用 `address_id`、`addr_id` 这类模糊命名。
- `user_address` 唯一键 `(account_id, geo_address_id, detail_addr, contact_name, contact_phone)`。`contact_name` 参与唯一键，允许同一地址使用不同收件人称谓。
- 软删除 + 复活：`deleted_at` 不参与唯一键；插入撞键后回查，若命中已软删行则更新全部业务字段并置空 `deleted_at`，`created_at` 保留原值。
- 默认地址不落库，由 App 端本地记录（按账号映射 `user_address_id`）。
- 坐标系统一 GCJ-02，`lng`/`lat` 拆 `DECIMAL(10,6)` 两列；入库坐标为 **POI 自身坐标**（`pois[].location`），不是用户定位点。
- 直辖市与省直辖县高德 `city` 返回空，入库时以 `province` 填充。
- 运单内联地址快照，不存 `geo_address_id`；缓存行更新不得改写历史订单。
- `geo_address` 永不物理清理，避免 `user_address.geo_address_id` 悬空。
- 并发不安全部交给唯一索引裁决；具体用 upsert 还是「先查后写 + 兜底异常」留到编码阶段定。
- 调用时序：首次录入（`regeo` + `extensions=all`，从返回 `pois` 中选点）**1 次**；`pois` 里没有目标时 fallback 周边/关键字搜索再 +1；再次选中同一 `poi_id` **0 次**；下单 **0 次**。
- `geo_address` 只存业务必需字段，不保存高德原始响应：保留 `raw_json` 只会带来列膨胀且无查询价值。

建表语句：

```sql
CREATE TABLE geo_address (
  geo_address_id CHAR(36)      NOT NULL COMMENT '地理缓存主键 UUID',
  poi_id         VARCHAR(64)   NOT NULL COMMENT '高德 POI ID，缓存键',
  poi_name       VARCHAR(128)  NULL     COMMENT 'POI 名称，如「XX小区」',
  adcode         CHAR(6)       NULL     COMMENT '高德行政区划码',
  province       VARCHAR(32)   NULL,
  city           VARCHAR(32)   NULL     COMMENT '直辖市/省直辖县高德返回空，入库时以 province 填充',
  district       VARCHAR(32)   NULL,
  lng            DECIMAL(10,6) NOT NULL COMMENT 'GCJ-02 经度，取自 POI 坐标',
  lat            DECIMAL(10,6) NOT NULL COMMENT 'GCJ-02 纬度，取自 POI 坐标',
  created_at     DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at     DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (geo_address_id),
  UNIQUE KEY uk_poi (poi_id),
  KEY idx_adcode (adcode)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 ROW_FORMAT=DYNAMIC COMMENT='地址地理缓存';

CREATE TABLE user_address (
  user_address_id CHAR(36)     NOT NULL COMMENT '用户地址条目 UUID',
  account_id      CHAR(36)     NOT NULL,
  geo_address_id  CHAR(36)     NOT NULL COMMENT '→ geo_address.geo_address_id',
  contact_name    VARCHAR(32)  NOT NULL,
  contact_phone   VARCHAR(20)  NOT NULL,
  detail_addr     VARCHAR(200) NOT NULL COMMENT '栋/单元/楼层/门牌',
  tag             VARCHAR(16)  NULL     COMMENT '家/公司/学校，仅展示',
  created_at      DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at      DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  deleted_at      DATETIME     NULL     COMMENT '软删除；复活时置空',
  PRIMARY KEY (user_address_id),
  UNIQUE KEY uk_account_recipient (account_id, geo_address_id, detail_addr, contact_name, contact_phone),
  KEY idx_geo (geo_address_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 ROW_FORMAT=DYNAMIC COMMENT='用户地址簿';
```

原因：

- 快递按「小区 + 楼栋 + 门牌 + 电话」送达，文本门牌是唯一可靠送达依据，坐标只用于打点、算距离与网点分区。
- 同楼不同楼层、同地址不同收件人的差异全部落在用户维度，缓存层只保留地理事实，重复行从「用户数 × 条目数」降到「唯一 POI 数」。
- 缓存键必须是不调 API 就能判定命中的稳定标识，`poi_id` 满足；文本地址不满足，同一地点写法各异。
- `regeo` 传 `extensions=all` 会同时返回 `addressComponent` 与 `pois`，一次调用即可拿到省市区与候选锚点，常规录入只花 1 次配额。
- 默认地址属客户端偏好，落库会引入跨端同步与「多默认」互斥逻辑，收益低于成本。
- `geo_address` 一旦清理就会让引用悬空，而其量级极小，直接定为不清理。
- 唯一键包含 `contact_name` 与 `contact_phone`，使「同一地址、不同收件人」成为不同条目，符合快递实际投递对象语义；代价是改名等于新条目，因此编辑必须走按 `user_address_id` 的更新接口，不得复用新增接口。
- 高德服务条款对长期存储有限制，只存业务必需字段可减少该风险面；商用前需再评估授权。

与 D-021 的关系：替代 D-021 中的 `user_address` 单表结构（原表内联 `adcode`/`poi_id`/`lng`/`lat`）；D-021 其余结论（文本权威、GCJ-02、运单内联快照、服务端反查 adcode）继续有效。

## D-023 地址两张表落地修正

问题：D-022 的建表语句没有显式 collation，`user_address.account_id` 未按新命名规则改名，`geo_address.adcode` 允许 NULL；而运单的 `sender_adcode` / `receiver_adcode` 是计费与揽派反查的硬前置。

决定：

- `geo_address.adcode` 改为 `CHAR(6) NOT NULL`；高德反查未返回 adcode 时拒绝缓存与下单。
- `geo_address`、`user_address` 所有字符列显式 `COLLATE utf8mb4_general_ci`，表尾补 `ROW_FORMAT=DYNAMIC`。
- `user_address.account_id` 改名 `auth_account_id`，`uk_account_recipient` 同步改列名。
- `waybill.sender_adcode`、`waybill.receiver_adcode` 改为 `CHAR(6) NOT NULL`；`waybill.pay_method` 改为 `TINYINT UNSIGNED NOT NULL`。

原因：跨表 join 避免 1267；跨表引用必须用全名；计费链路不允许 adcode 为空；支付单建单时机依赖 `pay_method`，不允许下单时未选。

## D-024 支付终止：业务终止事件 + 复活原单

问题：运单取消或退回时，未支付的寄付单与到付单没有关闭通道；到付超时介入与欠费结清若新建支付单，旧单会永远停在 `6` / `4`，欠费硬拦截永不解除；退回场景的 `event_outbox.biz_type` 没有合法值。

决定：

- `event_outbox.event_type=3` 由「创建退款」改为「业务终止（关单+退款）」。运单进入 `6已取消` 或 `8退回中` 时同一事务写入：取消场景 `biz_type=2 + waybill_cancel_id`，退回场景 `biz_type=1 + waybill_id`，两者都填 `waybill_id`。
- 支付服务消费：按 `waybill_id` 查 `biz_type=1` 的支付单；`status IN (1,3,6)` 置 `4已关闭`；`status=2` 建全额退款；无支付单直接成功。
- `refund_source` 由事件 `biz_type` 映射：`2 → 1运单取消`，`1 → 4运单退回`。
- 到付超时人工介入走 `6→1`，欠费结清走 `4→1`，均复活原单，不新建支付单。
- 支付成功撞 `uk_paid_biz` 时，本单不写 `paid_biz_key`，置 `status=2`、备注「重复支付，待人工退款」。
- 欠费催收用 `payment_reminder.remind_type=2` 留痕，第 1/3/7 天发送，以 `payment.closed_at` 为基准。

原因：补齐关单通道，避免用户为已终止业务付款；复活原单消除欠费死锁与迟到回调撞唯一键；单一事件同时覆盖取消与退回。

## D-025 入职申请即审

问题：人员草稿一方面写「申请提交后系统同步核验，无人工待审窗口」，另一方面在审核事务里再次 INSERT `approval`，会撞 `uk_biz`。

决定：申请提交即审核，一个事务内完成：校验凭证与账号 → 原子核销 `staff_training.voucher_used_at` → INSERT `staff_apply` → INSERT `approval(status=2, audit_operator_type=1)` → INSERT/UPDATE `logistics_staff` → INSERT `event_outbox`。任一环节失败整笔回滚，凭证保持未使用。

含义：不产生待审状态，不设驳回回滚；一个凭证最多对应一条成功申请单；`approval.status` 实际只出现 2，保留 1/3/4 为通用表结构与未来人工复核留位。

原因：消除重复写入 `approval`，与已裁决口径一致。

## D-026 撤并事务与退回交接单边界

问题：撤并只迁移 `logistics_site_area`，下级网点、员工、车辆会悬挂在停用网点；`direction=2` 的端点校验与撤并解引用冲突；在途退回在货未到达时用「最后已完成段」取起点，会选错网点。

决定：

- 撤并只允许同 `site_type` 之间进行。一个事务内：旧网点置停用、写 `logistics_site_merge`、迁移 `logistics_site_area`（仅 `site_type=1`）、迁移下级 `parent_logistics_site_id`、迁移 `logistics_staff.logistics_site_id` 与 `vehicle.logistics_site_id`。
- `direction=2` 只强制 `transport_line_id` 存在；起终点允许是撤并解引用后的新网点，未撤并时仍等于线路端点。
- 在途退回：发起时只写 `waybill_return`、置 `8`、写动作码 9；若存在正向在途段，第一张退回交接单延迟到该段到达并置 `status=2` 后创建。
- 每条 `route_rule.current_site_id` 必须等于对应 `transport_line.origin_site_id`。

原因：消除悬挂引用、必失败的校验与错误的退回起点；保证规则给出的下一跳从当前网点出发。

## D-027 运费试算接口口径

问题：计费规则的表结构已定，但接口行为、错误码与数值舍入在草稿里没有落地口径。

决定：

- 接口 `POST /logistics/price/quote`，放物流服务；只试算不落库，下单时再调一次并以落库结果为准。
- 寄收关系由 adcode 前缀判定：前 2 位不同为跨省；前 2 位相同且属于 `11/12/31/50` 为同城；前 4 位相同为同城；其余为省内。判定在代码中完成，不落表。
- 计费重量不做体积重，按续重单位向上取整：`units = ceil((weight - first_weight) / extra_unit)`。
- 金额统一 `BigDecimal` + `ROUND_HALF_UP` 保留 2 位；保价费取 `max(申报价值 × 费率, 最低保价费)`。
- 未申报保价时 `insuredFee=0.00`、`insuranceRuleId=null`；申报保价但无启用规则返回 500 `INSURANCE_RULE_MISSING`。
- 申报价值超过规则 `max_declared_value`（非 NULL 时）返回 422 `INSURANCE_LIMIT_EXCEEDED`。
- 错误响应沿用 RFC 9457 `ProblemDetail`，挂 `code` 与 `timestamp`，不引入统一壳。
- 报价接口暂不鉴权，物流服务鉴权方案统一在运单接口前定。

原因：先把最小独立的业务纵切跑通，用它固定物流服务的 `controller / service / mapper / dto / exp` 骨架，后续地址、运单、路由复用同一套结构。

## D-028 地址模块落地口径

问题：D-022 只定了表结构与录入流程，没有定接口形态、POI 归属行政区怎么取、令牌如何校验。

决定：

- 接口放物流服务：`GET /logistics/address/regeo`、`GET/POST /logistics/address/user`、`PUT/DELETE /logistics/address/user/{id}`。
- `regeo` 走高德 `v3/geocode/regeo`，`extensions=all`、半径 1000m、`sortrule=distance`，只返回不落库。
- 高德 POI 对象不返回 `adcode`/`pname`/`cityname`/`adname`，行政区一律取定位点的 `addressComponent`。语义正确：用户选的是自己位置附近的锚点，归属行政区由自己的定位决定。
- `regeo` 的 `adcode` 为空时返回 404 `ADDRESS_NOT_FOUND`，不落库。
- 地址簿鉴权：物流服务把 `Authorization: Bearer` 转发到 auth `POST /auth/verify` 换取 `accountId`，不在本地解析令牌；auth 返回 4xx 映射 401 `UNAUTHORIZED`，连不通映射 502 `AUTH_UNAVAILABLE`。
- 新增地址先按 `poi_id` 命中 `geo_address`，命中则刷新地理字段并复用，未命中才插入；并发撞 `uk_poi` 时回查已有行。
- 地址簿撞 `uk_account_recipient`：未删除行返回 409 `ADDRESS_DUPLICATED`；已软删行原地复活，`deleted_at` 置空、`tag` 覆盖、`created_at` 保留。
- 编辑地址换了 POI 时，同步把 `user_address.geo_address_id` 指向新缓存行。
- 高德 Key 走 `AMAP_WEB_KEY`，只落 `a_run_env/logistics.env`，`a_run_env_example` 只放占位符。

实测：Key 为 Web 服务类型时，`regeo`（`extensions=all`）在 1000m 半径下返回 30 条 POI，字段为 `id/name/type/tel/direction/distance/location/address/poiweight/businessarea`，无行政区字段。

补充：`place/text`（关键字搜索）返回的 POI 同样**不含** `adcode`，只有 `adname`（区名）、`cityname`、`pname`。因此新增任何「POI 搜索」类数据来源（如驿站批量导入）时，必须对选中 POI 的坐标再调一次 `regeo`，用 `addressComponent.adcode` 补齐后才能写 `geo_address`。`adcode` 不可用区名替代：区名全国重名，且计费按前 2/4 位判定、网点反查按 `adcode` 唯一键匹配。

原因：把 POI 行政区缺失、令牌校验、软删复活三个容易在实现期临时拍板的点固定下来，避免后续运单空运单地址时口径不一致。

## D-029 对外单号统一由数据库序列表生成

问题：运单号、交接单号、支付单号、退款单号都是「前缀 + yyMMdd + 定长日序号」，草稿只定了格式，没定生成方式。实现期容易因为「Redis INCR 更简单」临时决定。

决定：

- 所有对外单号由数据库序列表生成，不用 Redis。
- 每个服务在自己的库里建同构的 `biz_seq` 表，主键 `(biz, seq_date)`：物流库存 `WAYBILL`、`HANDOVER`，支付库存 `PAYMENT`、`REFUND`。
- 取号在业务事务内执行两条语句：

```sql
INSERT INTO biz_seq (biz, seq_date, current_seq) VALUES (?, ?, LAST_INSERT_ID(1))
ON DUPLICATE KEY UPDATE current_seq = LAST_INSERT_ID(current_seq + 1);
SELECT LAST_INSERT_ID();
```

- 日期按 `Asia/Shanghai` 取值，不依赖 JVM 默认时区。
- 唯一索引 `uk_waybill_no` 等作为最后兜底，撞键重试最多 3 次。
- 序号超过格式位数上限直接抛错，不静默扩位。

原因：单号是不可重建的业务事实，必须与业务数据同库同事务。Redis 在本项目只承担短期令牌与可重建缓存（项目规范 §2、D-007），未强制持久化，重启或掉电会造成重号、跳号，而唯一索引只能报错、无法恢复序号。

## D-030 交接单待发状态、运单网点快照与签收字段

问题：V1 的 `handover.departed_at` 为 `NOT NULL`、`status` 只有在途/已到达，无法支持「先扫码装车、后发车」；运单不存当前网点，装车时校验「下一跳线路」需要反推历史交接记录；运单没有任何签收人字段，他人代收无处登记。

决定：

- `handover.departed_at` 改可空，`status` 增加 `0待发`。交接单创建后为待发，装车可分批提交并幂等跳过，发车时写 `departed_at` 并置 1。
- `waybill` 增加 `current_site_id`：揽收时写寄件 adcode 归属网点，交接单到达时更新为 `to_site_id`。装车校验直接比较该快照，不再反推。
- `waybill` 增加 `sign_type`、`sign_name`、`sign_phone`：本人签收可空，他人代收必填姓名与手机号。驿站取件的取件人信息将来落 `station_parcel`，不占这三个字段。
- 放开 `2已揽收 → 4派送中`，用于揽收网点同时是派送网点的同城件。
- 交接单由在职员工创建，`from_site_id`/`to_site_id` 由线路带出，调用方不选线路。装车时由 `RouteResolver` 算出运单下一跳，与交接单线路不一致则拒绝。
- 交接单创建权限暂不区分调度与网点管理员，`logistics_staff.staff_role` 现有词表没有对应角色，先用「任意在职员工」，角色扩展另行处理。

原因：真实场站是调度排班次、现场逐件扫码、司机核验任务后发车，司机不选线路。原表结构只支持「已发车」的交接单，与装车顺序冲突；运单网点快照把每次装车的校验从多次历史查询降为一次字段比较；签收人信息是派送员的法定义务，必须有落点。

迁移：V6。

## D-031 支付建单与模拟支付口径（5-1）

决定：

- 支付单号 `P + yyMMdd + 8 位日序号`，payment 库自建 `biz_seq`，`biz` 取 `PAYMENT`、`REFUND`。
- 建单按 `biz_type + biz_id` 幂等，`status IN (1,2,6)` 视为未终结，命中直接返回已有单。
- 寄付（`payMethod=1`）由 logistics 下单事务内同步调 `POST /payment/orders`，失败整笔回滚。
- 到付（`payMethod=2`）下单不建单，等运单进入 `4派送中` 再建，属 5-3。
- 当前只接模拟渠道（`pay_channel=1`），支付宝沙箱留到 5-2。
- 模拟支付用条件更新 `WHERE pay_channel=1 AND status IN (1,3,6)` 抢唯一赢家；同业务已有成功单时，本单记重复支付，不写 `paid_biz_key`。

原因：`payment_no` 注释已声明可直接作渠道 `out_trade_no`，无需另加列；寄付必须与运单同生共死，否则会出现无法支付也无法揽收的孤儿运单；重复支付不能覆盖 `paid_biz_key`，否则唯一键会把正常回调打成异常。

迁移：payment V2。

## D-032 支付宝沙箱接入与模拟渠道对齐（5-2）

决定：

- 不引官方 SDK，移植 `cloudman` 项目的极简客户端：JDK `HttpClient` + `SHA256withRSA` 手写签名，只覆盖 `alipay.trade.precreate`、`alipay.trade.query`、异步通知验签。
- 三条签名规则原样保留：请求签名包含 `sign_type` 且用原始值；同步响应验签用业务节点原始文本；异步通知验签剔除 `sign` 与 `sign_type`。
- `payment_no` 直接作 `out_trade_no`，不新增渠道商户订单号列。
- `payment` 增加 `channel_pay_url` 存 precreate 的 `qr_code`（V3）。
- 支付渠道由订单入参 `payChannel` 决定，不做全局开关；logistics 下单透传，不传默认 1。
- 模拟渠道的渠道字段统一写 `MOCK-T-{paymentNo}`，退款写 `MOCK-R-{refundNo}`，保证与沙箱同一数据形态。
- 入账三态：正常、重复通知幂等、关闭后迟到支付（置 2、记 `pay_remark`、不占 `paid_biz_key`）。
- 异步通知公开无鉴权，安全性完全依赖验签；返回纯文本 `success`，金额与本地不一致返回 `failure`。

原因：官方 SDK 会带入 fastjson 与 httpclient4，与 Spring Boot 4 的 Jackson 3 并存增加依赖面；模拟渠道是沙箱不可用时的降级备份，必须与沙箱共享同一套字段与状态机，只在渠道适配层分叉。

迁移：payment V3。

## D-033 service 包拆分 support 与 routing

决定：`service` 只留以 `Service` 结尾的业务编排类；无状态复用件（单号生成、状态/权限守卫、费用关系推导）移到 `support`；路由子域（`RouteResolver`、`RoutingSnapshot`、`RoutingValidator`、`RoutingValidationRunner`）整体移到 `routing`。判定规则写入规范 §5，新增子域包先改规范表。`RoutingValidationRunner` 增加 `logistics.routing.validate-on-startup` 开关，默认 `true`。

原因：`service` 包曾混入 9 个非 Service 类，违反规范 §5「service 只做业务编排」，导致按包名无法判断职责。方案 A 比「全部平铺到 service」更能体现子域边界，也比「每个类单独建包」更轻。

影响：logistics 新增 `support`（5 类）、`routing`（4 类）；payment 新增 `support`（1 类）；7 个 Service 的 import 已同步。

## D-034 短信发送收敛到 sms-server

决定：`server8084-sms` 提供唯一发送接口 `POST /sms/send`；auth 删除 `sender` 包（`SmsSender`、`PboxSmsSender`），改由 `client/SmsClient` 调短信服务。模板以 `SmsTemplate` 枚举进代码，共 5 个：`LOGIN_CODE`、`PAY_REMIND`、`PAY_REMIND_FINAL`、`ARREARS_REMIND`、`ARRIVAL_NOTICE`。幂等键 `request_id` 由调用方生成，先查后发，重放返回首次结果；发送失败也返回 HTTP 200 + `result=2`，由调用方检查。落库前脱敏：验证码替换 `******`，支付链接只留 `scheme://host` 与末段短码。pbox 凭证只留在 `sms.env`。

原因：短信是各服务共用的基础设施，凭证、重试、脱敏、幂等应由一处承担；auth 直连 pbox 会让每个新调用方重复实现一遍。

影响：auth 新增 `client/SmsClient`，`AuthProperties.Sms` 去掉 `Pbox` 加 `baseUrl`，`AuthBeanConfig` 的 `pboxRestClient` 改名 `smsRestClient`；`auth.env` 删 3 个 `PBOX_*`、加 `SMS_SERVICE_URL`。sms 新增 13 个类，无新迁移（`sms_record` 已足够）。契约见 `sms-server接口契约.md`。

## D-035 跨服务 DTO 收进 xxx-api 模块，对外模型改 VO

决定：新增 `auth-api`、`payment-api`、`sms-api` 三个纯 Java 模块，放服务间 DTO、路径常量与码值；服务模块的对外模型从 `dto` 改名为 `vo`，统一后缀 `ReqVO` / `RespVO`。服务间接口统一 `/xxx/internal/**`：`/auth/internal/verify`、`/payment/internal/orders`、`/sms/internal/send`；对外 `/auth/verify` 保留给 App。高德返回结构改放 `client/model/amap`，由 `AddressService` 映射成 `RegeoRespVO`。

原因：此前同一份 DTO 同时服务 App 和内部调用，`PaymentCreateRequest` 是最典型的一例；内部加字段会污染外部契约。按 yudao-cloud 的模块 API 模式拆分后，双方编译期使用同一份类，同时外部与内部契约互不影响。`contract` 继续只放 Android 也依赖的跨端常量。

影响：logistics 17 个类、auth 7 个类、payment 1 个类改名为 VO；删除 6 个 client 内镜像 record；新增 3 个 `xxx-api` 模块与 10 个类；3 个服务增加对 api 模块的依赖；4 份接口契约同步路径。无数据库迁移。

## D-036 业务终止事件走手动投递，退款在支付服务内闭环

决定：logistics 的 `event_outbox` 投递不接定时任务，先暴露 `POST /logistics/internal/outbox/dispatch` 手动触发。`OutboxDispatchService` 按 `target_service=3` 拉取 `status IN (1,3)` 的事件，逐条调 payment `POST /payment/internal/biz-terminated`；成功置 2，失败按 `retry_count` 置 3 待重试，满 3 次置 4 已放弃并记 `last_error`。payment 侧按 `waybill_id` 取该运单全部支付单：待支付/支付失败关单，已支付建全额退款；模拟渠道即时退款成功并写 `payment_outbox(event_type=2)`，支付宝渠道只建 `refund(status=1)` 待退款。`refund_source`：运单取消 → 1，运单退回 → 4。

原因：定时任务需要退避、告警与放弃事件的处理口径，先用手动接口打通链路，避免把未定策略固化进代码；退款判定放在支付服务内，物流侧只负责产生「业务终止」这一事实，不关心支付单状态。

影响：payment-api 新增 `PaymentCreateRespDTO`、`BizTerminatedReqDTO`、`BizTerminatedRespDTO` 与 `BIZ_TERMINATED` 路径；payment 新增 `RefundMapper`、`PaymentOutboxMapper`、`PaymentSettlementService`，`PaymentMapper` 加 `findByBizAll`、`markRefunded`，`PaymentNoGenerator` 加 `nextRefundNo`（复用 `biz_seq` 的 `REFUND`）；logistics 新增 `OutboxDispatchService`、`InternalOutboxController`、`EventOutboxRow`，`EventOutboxMapper` 加 4 个状态流转方法，`PaymentClient` 加 `notifyBizTerminated`。定时任务与支付宝退款渠道分别记 `E-09`、`E-10`。

## D-037 当前阶段只做一条主闭环

决定：本阶段只完成「App 下单并寄付 → 揽收 → 网点装车发车 → 转运中心 → 干线运输 → 派送网点 → 签收」这一条链路。到付与欠费、驿站完整运营、退回运输、路由撤并、实名认证移出本阶段，保留在待办。进度统一记在 `待办/闭环任务清单.md`。

原因：闭环优先，先把能端到端演示的链路跑通，避免支付、驿站、退回多线并行导致每条都不完整。

影响：`F-15` 标注闭环外；新增 `E-11`、`E-12`；新建 `闭环任务清单.md` 作为本阶段唯一进度视图。

## D-038 员工数据由 App 注册产生，不使用 SQL 种子

决定：不在 Flyway 迁移里写死员工与员工账号。员工身份通过 App 的注册/入职入口真实产生。当前阶段该页面只做 UI，不接任何接口；后端入职接口随后单独一轮实现。

原因：种子数据无法演示「账号注册 → 员工身份 → 在职」的真实业务；写死 BCrypt 哈希与固定账号也会污染迁移脚本。

影响：`logistics_staff` 当前无数据，所有员工接口返回 403 `STAFF_FORBIDDEN`，员工侧流程在入职接口完成前只能等。`C-01` 只交付页面，`C-06` 才接真实后端。

## D-039 培训凭证按岗位签发

决定：`staff_training` 新增 `staff_role`，`NOT NULL` 且不设默认值，由签发方显式指定。同一账号同一岗位只保留一条凭证，唯一键 `uk_account_role(trainee_auth_account_id, staff_role)`。入职申请的 `apply_staff_role` 必须与凭证的 `staff_role` 一致。

原因：培训内容与岗位强相关，客服与快递员的培训不可互换；默认值会让签发出错时被静默归为快递员。

影响：新增迁移 `V7__add_staff_training_role.sql`；发证接口入参必填 `staffRole`；入职接口核验时增加岗位一致性判断。

## D-040 姓名以 auth 为唯一权威

决定：`auth_user_profile.real_name` 是姓名的唯一可写入点。任何服务、脚本、接口都不得自行构造或覆盖姓名；业务表（`logistics_staff.staff_name`、`staff_training.trainee_name`）只存展示快照。发证接口不接收姓名参数，`real_name` 为空时拒绝发证，返回 422 `REAL_NAME_REQUIRED`。

原因：姓名是多服务共用的身份信息，任一处可写会产生不一致；快照只解决展示与历史留痕，不承担权威职责。

影响：`staff_training.trainee_name` 注释由「培训时登记」改为「发证时取自 auth」；发证脚本只输手机号，姓名由服务端从 auth 读取。

## D-041 培训凭证不做核销，使用即失效

决定：删除 `staff_training.voucher_used_at`。凭证只有「有效 / 失效」两种状态：`voucher_expire_at > now()` 为有效；过期或入职成功后把 `voucher_expire_at` 置为当前时刻即失效。不设核销标记，不做审核。过期凭证的重新激活接口本轮不实现，记待办 `E-13`。

原因：一个账号在凭证时效内不可能完成两次培训，核销标记属于冗余状态；用有效期表达生命周期更简单，也避免核销与审核两套状态并存。

影响：`V7` 删除 `voucher_used_at` 并新增 `uk_account_role`；入职核验去掉「未核销」条件；发证接口对同账号同岗位已有凭证返回 409 `VOUCHER_EXISTS`。

## D-042 发验证码前校验手机号已在短信沙盒登记

决定：`SmsCodeService.sendCode` 第一步调 sms-server `GET /sms/internal/phones/exists`，`registered=false` 返回 422 `PHONE_UNREGISTERED`，不发码。sms-server 转发 pbox 的 `GET /sms/phones/exists`，不为 auth 单独开 pbox 配置。

原因：pbox 是沙盒，未登记的号码收不到短信；提前拦截比发出去再失败更清晰，也符合 D-034「短信基础设施收敛到 sms-server」。

影响：sms-api 新增 `PHONE_EXISTS` 路径与 `PhoneExistsRespDTO`；auth 新增错误码 `PHONE_UNREGISTERED`；注册流程的发码环节因此多一次内部调用。

## D-043 密码只设上限，不设下限

决定：注册接口的密码校验从 `8~64` 改为 `max=64`，App 注册页同步去掉 8 位下限。登录接口本来就只限 64 位上限。

原因：演示账号统一使用 `123456`，便于测试；下限只存在于注册一侧，去掉后前后端口径才一致。

影响：`RegisterReqVO` 与 App 注册页同步修改。风险是弱密码，生产环境需恢复强度要求或增加复杂度校验。

## D-044 入职同步授予角色，不依赖 outbox 投递

决定：`POST /logistics/staff/apply` 在写员工、申请、审核的同一事务内，同步调 auth `POST /auth/internal/roles/grant` 授予 `role_id=2`；失败整笔回滚。`event_outbox` 仍写一条授予角色事件，仅作审计与后续补偿，不作为生效依据。重复提交先判员工身份返回 409，再校验凭证。

原因：outbox 投递器还没实现，靠异步授予会让登录响应里的 `roles` 仍为 1，App 无法立即识别员工身份；auth 授予接口幂等，同步调用失败回滚不会出现「有员工记录但没有员工角色」。

影响：auth-api 新增 `GRANT_ROLE_INTERNAL`、`RoleGrantReqDTO`、`RoleGrantRespDTO`；logistics 新增 `StaffApplyService`、`StaffController`、`staff_seq` 迁移（工号 `KD-` + 8 位）；`WebConfig` 增加 `/logistics/staff/**` 鉴权路径。

## D-045 首页地图用高德 Android SDK 在线瓦片，包名以高德控制台为准

问题：首页地图怎么接、Key 怎么放、手势与定位怎么处理。

决定：
- 依赖只用 `com.amap.api:3dmap:10.0.600`；该包已内置定位 SDK（`AMapLocationClient`），再引 `com.amap.api:location` 会产生重复类导致构建失败。
- `applicationId` 改为 `me.feseis.fish`，与高德控制台 PackageName 对齐；`namespace` 与 Java 包名仍为 `com.feseis.fish`，两者本就允许不同。
- Key 存根目录 `key.properties` 的 `amapKey`（不入库），经 `manifestPlaceholders` 注入 Manifest 的 `com.amap.api.v2.apikey`，不硬编码进仓库。
- 地图手势全部保留；手指从地图上按下时 `requestDisallowInterceptTouchEvent(true)`，避免外层 `ScrollView` 抢走拖动事件。
- 定位蓝点用 `AMapLocationClient` + `LocationSource`，首次定位成功相机居中一次，之后不跟随，避免与用户拖动打架。
- 地图与定位两个 SDK 的隐私合规声明集中在 `FishApp.onCreate()`，先于任何地图/定位对象创建。

原因：地图 SDK 的瓦片由 App 内 SDK 直连高德，不消耗 Web 服务 API 配额；包名与 SHA1 是高德鉴权的硬条件；Key 不入库沿用 D-020 策略；禁用地图手势与用户预期不符；一次性居中比持续跟随更可控。

影响：App 包名变更后旧安装包会并存且本地登录态不继承；换构建机需在高德控制台补该机 debug SHA1；地图空白时按「包名 → SHA1 → Key → 隐私合规初始化」顺序排查。

## D-046 地址簿只保留单一「我的地址」列表，默认地址存本地

问题：是否照搬顺丰的「我的地址 / 顺丰地址」双分组地址簿。

决定：
- 取消双分组，只保留「我的地址」一个列表，复用 `user_address` 现有结构与接口，后端零改动。
- 默认地址不落库，App 端 `SharedPreferences` 按 `auth_account_id` 记一个 `user_address_id`；删除默认项时同步清空。
- 录入链路沿用 D-022「定位 → regeo → 选附近 POI → 填门牌」，POI 必选。
- 智能识别与分机号本轮不做，记待办 `F-07`。

原因：两个分组在表结构、唯一键与 CRUD 上完全同构，分组只增加一层没有业务收益的维度；默认地址属于设备偏好，放本地可避免后端为此加表或加列。

影响：地址簿只调用 `/logistics/address/user` 与 `/logistics/address/regeo`，接口契约不变；后续下单页默认选中本地记录的默认地址。

## D-047 地址选择支持关键字搜索，默认限定当前城市

问题：地址录入只能定位后从附近 POI 中选，无法主动查找某个地点。

决定：
- 新增 `GET /logistics/address/search`，后端调高德 `v3/place/text`，`offset=20`。
- 客户端把当前定位城市一并传入，后端用 `citylimit=true` 限定；定位失败或尚未定位时不传城市。
- 只在点击「搜索」或键盘搜索键时请求，不做输入即搜，避免快速消耗高德 Web 服务配额。
- 「重新定位」恢复附近 POI 并清空关键字。

原因：关键字搜索是 D-022 中预留的 fallback；限定城市可避免跨省同名地点干扰；手动触发保护个人 Key 的每日配额。

影响：`AddressController` 新增 `/search`，契约 §4.1；App `PoiPickerActivity` 增加搜索框；`PoiPickerActivity` 与 `AddressBookActivity` 的 inset 监听改为在系统栏基础上叠加 20dp，修复边距被 `setPadding` 覆盖的问题。

## D-048 首页只负责选寄收地址，选齐后才出现寄件入口

决定：
- 首页寄、收两行只做地址选择：未选时显示「填写取件/收件地址」，已选后显示完整地址与联系人、手机号。

## D-049 首页地址走一次性填写页，不强制入地址簿

问题：首页点寄/收直接进地址簿，等于强制所有地址先入库，而实际存在大量一次性地址。

决定：
- 新增 `AddressEntryActivity`，点首页寄/收行进入：可手填门牌/姓名/电话，地址栏点击走 POI 选择或搜索，右侧「地址簿」仅作为可选回填入口。
- 默认只写入内存草稿 `ShipmentDraftStore`，不调用地址簿接口。
- 表单提供「保存到地址簿」开关，默认关闭；打开后才调 `POST /logistics/address/user`。
- 首页右侧「地址簿」胶囊保留，直接进地址簿选择模式，作为已存地址的快速路径。
- 已选地址再次点开进入同一填写页并回填，用于修改或更换。

原因：一次性地址不应产生地址簿数据；把「填写」与「入库」解耦，同时保留常用地址的快速选择。

影响：`HomeFragment` 行点击改为进入 `AddressEntryActivity`，胶囊进地址簿选择；新增 `AddressEntryActivity` 与布局。地址簿、后端接口均不改。
